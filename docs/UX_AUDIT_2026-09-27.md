# Revue UX PackQuest — 27 septembre 2026

## Périmètre vérifié

Version locale actuelle : démonstration parent/enfant avec mission en mémoire, bibliothèque de modèles locale en développement et bibliothèque liée au compte dans le build de production. Les six routes `/parent`, `/parent/new`, `/parent/mission`, `/parent/templates`, `/child` et `/child/mission` ont été examinées dans le code et dans le navigateur. Le parcours de démonstration a été exécuté sur téléphone : création d'une mission, démarrage, états d'affaires, demande d'aide, réponse parent, puis préparation renseignée avec un problème toujours visible. Le tableau de bord a aussi été inspecté à 360, 800 et 1280 px de large. Le build de production a été ouvert localement, y compris son écran de connexion aux modèles ; aucune connexion à un vrai compte n'a été effectuée.

## Corrections réalisées

- Navigation parent raccourcie et cibles tactiles principales agrandies. L'action « Nouvelle mission » reste accessible par le bouton principal du tableau de bord sur les écrans très étroits.
- Mise en page tablette corrigée : statistiques sans chevauchement, progression lisible et illustration retirée lorsque l'espace manque. L'éditeur de modèles passe en une colonne sur tablette.
- Mission de test : période modifiable, modèle vide inutilisable, et distinction explicite entre modèles locaux et modèles d'exemple dans le build de production.
- Tableau de bord : texte adapté à l'état reçu, commencé ou renseigné ; demandes d'aide comptées comme demandes ; liens des affaires signalées dirigés vers l'affaire concernée.
- Remise à zéro de la mission de démonstration confirmée avant effacement et retirée de l'écran des modèles, où elle n'avait pas d'effet visible.
- Éditeur de modèles : raisons d'un enregistrement impossible affichées, limites de saisie cohérentes avec la validation, modèles modifiés signalés et confirmation avant de quitter la page sans enregistrer.
- Checklist enfant : retrait d'un message de récompense qui restait affiché comme un nouvel événement ; une mission sans affaire ne peut pas être déclarée renseignée.
- Écran compte : erreurs de connexion et de chargement formulées pour un parent ; action « Réessayer » en cas d'échec de chargement.
- Bibliothèque de modèles chargée à la demande. Le build est passé de 536 Ko de JavaScript dans un seul fichier à 360 Ko initiaux et 233 Ko chargés uniquement pour cette route, avant compression.

## État de validation

- `npm run build` : réussi après les changements.
- `npm run lint` : aucune erreur ; deux avertissements préexistants sur Fast Refresh et un `setState` dans un effet.
- Navigateur local : boucle parent/enfant de démonstration parcourue ; réponse parent retrouvée côté enfant ; préparation renseignée à 15/15, dont une affaire introuvable. Dans l'éditeur, une affaire incomplète bloque l'enregistrement avec une raison visible ; la sortie affiche un choix, puis l'enregistrement permet de quitter.
- Build de production local : accueil, création de mission de test et entrée de la bibliothèque de compte affichés. Authentification et sauvegarde distante non vérifiées.

## Conditions avant une publication comme produit utilisable

Le build actuel peut être présenté comme **démonstration** avec ses avertissements visibles. Il ne satisfait pas encore le parcours du MVP connecté décrit dans le PRD : les missions et actions enfant se réinitialisent au rechargement, l'enfant n'est pas appairé à un profil, la mission de test du build de production utilise des modèles d'exemple distincts de ceux du compte, et il n'existe pas d'historique persistant ni de reprise hors ligne de la checklist. L'authentification réelle, les redirections, les migrations et politiques RLS, ainsi que les parcours sur deux appareils n'ont pas été vérifiés dans cette revue. Le dossier n'est pas initialisé avec Git ; aucune publication n'a été effectuée.

Avant de qualifier le **MVP** de prêt au déploiement, terminer les tranches connectées du PRD puis vérifier les parcours parent, enfant et suivi sur données persistantes, la sécurité serveur, la résilience hors ligne prévue et la configuration de l'environnement cible. Ne pas présenter le succès du build ou cette revue locale comme une validation de production.
